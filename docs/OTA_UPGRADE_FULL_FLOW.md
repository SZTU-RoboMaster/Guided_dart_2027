# Guided Dart LoRa OTA 升级全流程

本文按当前工程代码说明一次 App 无线升级从构建到验收的实际路径。这里的 A/B 指外挂 W25Q128 中的两个**镜像槽**；STM32 内部 Flash 只有一个可执行 App 区，不能把它理解为可直接启动两个内部 App 的双分区系统。

## 1. 使用前提与镜像选择

1. 目标板已通过首次 SWD 安装当前 Bootloader 和有效 App；Bootloader 本身不通过此 OTA 更新。
2. 两端 LoRa 模块处于正常透明传输模式，并使用相同的信道、空口速率等无线参数。电脑端选择实际枚举的 COM 口；主控 LoRa 使用 USART1，数据 UART 为 `115200 8N1`。串口波特率与空口速率是两个不同参数。
3. 目标板外挂 W25Q128 可读写，电源在擦写期间保持稳定。升级时不要同时下载原始 IMU 日志。
4. 构建命令在 OTA 根目录运行：

   ```powershell
   cd D:\JetBrains\CLionworkspace\Guided_dart_2027_ota
   .\build_all.ps1 -Configuration Release -Version 1
   ```

5. 上位机无线升级时选 `out\firmware\Guided_dart_app.bin`。不要选 `Guided_dart_app_swd.bin`、`Guided_dart_initial_full.bin` 或 ELF；它们含元数据或 Boot 内容，不是无线协议要传的独立 App 字节流。上位机会检查长度、初始栈和复位入口。

`-Version` 写入首次烧录用整片镜像的内部元数据；无线升级时，上位机将所选独立 App BIN 的 CRC32 同时作为本次版本标识，以便相同文件重新升级时匹配断点续传会话。因此无线升级后的版本值不一定等于构建命令中的 `-Version` 数字。

首次安装或维护可用 `tools\flash_swd.ps1` 的 `Boot`、`App`、`BootApp`、`All` 模式；其镜像和地址说明见 [BUILD_GUIDE.md](../BUILD_GUIDE.md)。普通升级不要求重新有线烧录。

## 2. Flash 分区与安全边界

| 存储 | 地址或偏移 | 大小 | 作用 |
| --- | --- | ---: | --- |
| STM32 内部 Bootloader | `0x08000000` | 16 KB | 接收 OTA、校验并启动 App |
| STM32 内部 App | `0x08004000` | 110 KB | 唯一可执行 App |
| STM32 内部元数据 | `0x0801F800` | 2 KB | App 长度、CRC32、版本及提交标志 |
| 外挂 Slot A / Slot B | `0x000000` / `0x020000` | 各 128 KB | 旧/新 App 镜像及 32 字节槽位头 |
| 外挂活动槽元数据 | `0x040000` | 4 KB | 当前活动镜像槽编号 |
| 外挂陀螺校准 | `0x050000` | 4 KB | 零偏记录 |
| 外挂 OTA 会话 | `0x060000` | 4 KB | 断点续传检查点 |
| 外挂原始 IMU 日志 | `0x080000` | 8 MB | 循环采样区，不覆盖 OTA 槽位 |

无线接收时先写**非活动**外部槽，内部 App 不被擦除。只有收到 END 并验证新槽整包 CRC32 后，Bootloader 才擦除内部 App 和元数据页、复制新镜像、重算内部 CRC32，最后修改活动槽指针。这个顺序能避免普通传输中断破坏当前 App；但内部复制期间掉电仍可能使内部 App 暂时无效，需下次启动从旧活动槽恢复。

活动槽元数据采用擦除后重写，不是断电原子事务；镜像 CRC 也不等于应用健康检查。因此当前设计不承诺“任意时刻掉电均自动回滚到旧版本”，更不承诺新 App 虽能通过 CRC 但运行崩溃时自动回滚。

## 3. 协议与状态机

统一 LoRa 帧以 `A5 5A` 开始，含协议版本、消息类型、序号、时间戳、1 字节载荷长度、载荷及帧 CRC16。最大帧长 58 字节，最大载荷 45 字节。OTA DATA 载荷还要放 `chunk` 两字节和实际数据长度一字节，因此每块固件最多 42 字节。独立 App 最大 110 KB，对应最多 2682 块。

| 阶段 | 上位机发送 | 目标端动作 | 成功标志 |
| --- | --- | --- | --- |
| 进入升级 | `UPDATE_BEGIN`：镜像长度、CRC32、版本，各 4 字节小端 | App 收到后写 RAM 升级请求标志，先回状态 `0xFE`，再复位；Boot 收到后匹配旧会话或准备备用槽 | Boot 对 BEGIN 回状态 `0`，并给出 `next_chunk` |
| 传输 | `UPDATE_DATA`：块号、长度、最多 42 字节 | Boot 要求块号顺序连续，写入外挂备用槽并更新运行 CRC32 | 正常每 4 块累计 ACK；末块立即 ACK，ACK 值为下一待发块号 |
| 提交 | `UPDATE_END` | 检查总长度/CRC32，写槽位头，复核外部镜像，复制内部 App，写元数据并复核内部 CRC，最后切活动槽 | END ACK 状态 `0` 表示镜像已提交；Boot 随后复位 |
| 验收 | `DEVICE_INFO` | 新 App 上报内部元数据里的版本和 CRC32 | 两值均与此次所选 BIN 一致，上位机才显示“升级成功” |

ACK 的 4 字节载荷依次是 `next_chunk`（小端 2 字节）、原消息类型（1 字节）、状态码（1 字节）。BEGIN 的 `0xFE` 只表示旧 App 即将复位，不是 Boot 已准备接收 DATA。DATA 状态 `2` 表示块序不符，上位机会依据 Boot 返回的块号修正发送位置；`3` 表示外部写入或会话检查点失败。END 状态 `4` 表示长度或 CRC32 不符，`5` 表示最终存储/内部安装失败。BEGIN 状态 `1` 表示会话准备失败。

Boot 每 64 块或最后一块在外挂 Flash 追加一个持久化检查点。重启后再次发送**同一 BIN**，BEGIN 按镜像长度、CRC32、版本以及槽位匹配检查点；从最近有效 `next_chunk` 继续。最近检查点之后已写入但未确认的块可能重发。上位机先探测旧版逐块 ACK，必要时切换到新版 4 块累计 ACK；一个窗口无确认最多尝试 3 次。

## 4. 上位机实际操作

1. 给目标板供电，电脑端 LoRa 接串口转 TTL，并确保两端模块已经按工程参数配对且均处于透明传输模式。
2. 打开上位机，选择当前电脑端模块的 COM 口并点击“连接”。先用界面的链路测试确认 `DEVICE_INFO` 有回复。不要把历史上的 COM19/COM23 当成固定端口。
3. 切到“无线升级”，选择最新构建产物 `Guided_dart_app.bin`，点击“开始无线升级”。界面会依次显示请求 Boot、进入 Boot、发送块、校验并写入 App、等待新 App 确认。
4. 等待明确的“升级成功：新 App 已重启并确认版本/CRC”。进度条到 100% 仅表示数据发送完或镜像正在提交，不能单独当成成功依据。
5. 若链路中断，保持同一 BIN，恢复供电和链路后再次点击升级，让 Boot 使用检查点续传。若换了 BIN，Boot 将把它当作新会话并重新擦写备用槽。

当前上位机 BEGIN 最多发送 12 次，间隔约 800 ms；Boot 正常启动有 3 秒接收窗口。END ACK 最长等待 30 秒，然后上位机多次查询新 App 的版本及 CRC32。失败时请保留界面具体错误消息，区分“无线接收失败”“安装失败”和“镜像已提交但新 App 未确认”。

## 5. 掉电、失败与恢复

| 现象 | 当前代码行为 | 建议 |
| --- | --- | --- |
| 传输中断，尚未发送 END | 旧内部 App 不受新槽接收影响；会话检查点保留 | 恢复链路后用同一 BIN 重新升级 |
| DATA 块错误或 CRC16 错误 | 帧或块被拒绝，Boot 不推进有效进度 | 检查两端无线参数、电源、天线及串口；允许重传 |
| END 的长度或 CRC32 不符 | 新镜像不提交，旧活动槽不切换 | 重新用原 BIN 传输；持续复现时检查 Flash 和链路 |
| 内部 App 安装中断且内部 CRC 无效 | 下次启动尝试从旧活动外部槽恢复 | 保持供电后重启并重试；恢复失败时可能需要 SWD 检修 |
| END 已成功，DEVICE_INFO 没确认 | 上位机判为失败；可能是复位/无线回复丢失，也可能新 App 未正常启动 | 先重试链路测试和设备信息，不要仅凭 100% 进度判断成功 |
| 新 App CRC 正确但运行后崩溃 | Boot 只做镜像完整性校验，不做运行健康确认 | 当前没有自动运行期回滚；可能需要 Boot 接收恢复或 SWD |
| Bootloader 本身损坏、外挂 Flash 不可读或活动指针异常 | 无线恢复能力不保证可用 | 需要现场供电/硬件检查；必要时通过 ST-Link 修复 |

“可以重新进入 Boot 无线升级”依赖 Bootloader、供电和 LoRa 通路仍正常，不能把无线恢复写成所有故障都无需有线手段的保证。

## 6. 验证与交付口径

构建脚本已包含协议测试、LoRa 参数测试及整片镜像/App-SWD 镜像校验。修改 OTA 代码后至少执行：

```powershell
cd D:\JetBrains\CLionworkspace\Guided_dart_2027_ota
.\build_all.ps1 -Configuration Release -Version 1
```

实机验证应额外覆盖完整升级、故意断开再用同一 BIN 续传、上位机最终 `DEVICE_INFO` 校验，以及断电恢复。离线编译和协议测试只能证明软件构建及部分协议逻辑正确，不能替代实际 LoRa/Flash 闭环测试。本轮只整理注释与流程文档；没有据此推断硬件已重新验证。
